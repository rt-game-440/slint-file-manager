# 缩略图路线与性能测量基线（Issue #5 原型结论）

日期：2026-11-08。原型代码：[`prototypes/thumb-probe`](../../prototypes/thumb-probe)（独立 crate，不属于主程序）。测量入口：[`scripts/perf-thumbs.ps1`](../../scripts/perf-thumbs.ps1)。实现者是 #10。

本文只写本机实测过的内容。没有测的一律写“未测量”或“未覆盖”，不会写成 0，也不会据此推断。**本文不声称 Issue #1 的 200 ms／1 s／300 ms 三个目标已经达成**：原型是无头的（不含 Slint 上传与渲染），产品里还没有缩略图，目标只能由 #10 实现后用第 8 节的事件复测。

## 1. 结论（给 #10 的一页）

1. **WebP 走 libwebp 的“解码时缩放”**（`WebPDecoderConfig.use_scaling`，Rust 里用 `libwebp-sys`）。**这条结论的前提是有损且不透明的 WebP**（相机和手机导出的常见形态，Issue #1 的真实案例也属此类，但原型里是合成图，**真实文件未测**）：256 px 缩略图每张约 19 ms（单线程，1180 万像素），峰值内存只增加约 1.2 MiB；对比整幅解码再缩放（36 ms、+51 MiB）和纯 Rust 的 `image` + `webp`（130 ms、+83 MiB）都明显更好。1.44 亿像素的有损不透明 WebP 也只用 120 ms、1.8 MiB，另外两条路线分别是 +563 MiB 和 +964 MiB。
   **无损 WebP 和带透明的有损 WebP 不享受这个内存优势**：libwebp 仍要分配整幅缓冲，1200 万像素分别峰值 +54.6 MiB（92 ms）和 +70.4 MiB（40 ms）。所以像素上限对 WebP 也不能省，见 6.3。
2. **Windows Shell（`IShellItemImageFactory`）不作为 WebP 的主路线**：冷态每张约 113 ms（对平滑 WebP 比 libwebp 慢约 6 倍；对细节密集 WebP 约 1.7 倍；对 JPEG 约 2.2 倍）。**Shell 的提取在系统侧是串行的**：1、2、4 线程的吞吐都约 9 张/s（8.8／9.3／9.2～9.4，4 线程重复 3 次），并发只拉长单张延迟（4 线程均值 417～423 ms，且每次都出现单张最长约等于总时长的拖尾，6.4～6.5 s）。它的热路径很快（3.7 ms／张），但依赖系统 thumbcache，取决于机器上有没有 WebP 解码器（本机能出图，其他机器和 Win11 没有验证）。它保留给“本应用自己解码不了的格式”（视频、HEIC、PDF、Office 等）和云占位文件的 `INCACHEONLY` 查询（见 0003）。
3. **JPEG／PNG／BMP／GIF 用 Rust `image` 即可**：1200 万像素 JPEG 30 ms、PNG 58 ms、BMP 43 ms，都比 Shell 冷态快。但 `image` 要整幅解码（+82～115 MiB／张），所以必须加像素上限（第 6 节）。这只说明“能用、够快”，并没有和 JPEG 的 DCT 缩放、WIC 等备选比较过（第 7 节）。
4. **调度**：首屏可见项优先，滚动后丢弃排队中的请求，在途解码不能中断（只能丢弃结果）；每个结果都带“目录代数 epoch + 文件标识 key”，界面绑定时核对，结果不会贴到错的项上；慢文件 300 ms 后临时增援一个工作线程，2 s 硬超时显示回退图标，迟到的成功结果照常补上。第 4 节的实测支持这套设计。
5. **缓存**：进程内存缓存 + 磁盘缓存，磁盘缓存用有损 WebP q80（键 = FNV-1a(路径｜大小｜修改时间｜缩略图尺寸)）。同进程再进入 0.02 ms，重启后 28 项 2.3 ms，足以满足 300 ms 的重复访问目标（仍是无头下界）。
6. **工作线程数**：4 线程时 28 项冷首屏约 178 ms，6 线程约 139 ms；细节密集的 WebP 每张约 136 ms，12 张 4 线程要 457 ms，按此外推 28 张约 1.1 s（外推，没实测），所以线程数不要固定成 4，建议取 `min(逻辑核数 - 2, 6)`，给界面线程留出核心。弱 CPU 上的取值没有数据。
7. **不提前造通用后端框架**：#10 先实现“WebP → libwebp 缩放”这一条，其他格式先显示类型图标；JPEG／PNG 等用 `image`，Shell 只在确有需要的格式出现时再接。原型里的 `Route` 枚举只是为了对比，不要照搬进产品。

## 2. 测量方法与条件

### 2.1 事件定义

| 名称 | 定义 | 状态 |
| --- | --- | --- |
| 可操作 | 用户进入目录后，新目录内容的第一帧渲染完成（`dir-ready-us`，起点是发起进入）。沿用 #4 与 `docs/debug-harness.md` 的定义，不含缩略图 | 已有，产品里可测 |
| 正常文件首屏 | 首屏可见项里，除“失败／超时／不支持”项以外，全部已经绘制出缩略图的时刻（事件 `thumbs-first-screen-us`，起点与可操作相同）。失败、超时、不支持的项显示回退图标，**不计入**等待，但必须同时报告它们的数量：如果整个目录都失败，这个指标会很小而没有意义 | 产品未实现，显示“未测量” |
| 慢文件 | 超过 `slow_after`（300 ms）仍未返回的单张。其后增援线程，超过硬超时（2 s）则显示回退图标；迟到的成功会补上，状态为 `ready_late` | 原型验证 |

### 2.2 窗口、首屏项数、环境

- 窗口：产品初始窗口 1100×720，网格 7 列，**完整可见 4 行 = 28 项**；算上半露出的一行是 35 项。原型默认首屏 28，另测 35。
- 环境：Windows 10 专业工作站版 build 19045（Win11 无环境，未覆盖）；AMD Ryzen 5 9600X（6 核／12 线程）、47.2 GiB、NVMe SSD；Rust 工具链见 JSON 的 `env.rustc`。
- 缩略图尺寸 256 px（最长边，不放大），RGBA8 非预乘 alpha（与 Slint 的 `Rgba8Pixel` 一致）。
- 脚本把以上全部写进结果 JSON 的 `env`，包括 `os_file_cache`。

### 2.3 缓存条件（冷／热／重启）

| 条件 | 含义 | 怎么得到 |
| --- | --- | --- |
| 冷 | 进程内没有缓存、磁盘缓存为空 | 清空缓存目录，新进程第一次进入 |
| 同进程热 | 同一进程第二次进入同一目录 | 每个进程只有 1 次热通过，重复 N 个进程取中位数 |
| 重启 | 磁盘缓存保留，进程是新的 | 保留缓存目录，新进程第一次进入 |

**操作系统文件缓存不受控**：夹具刚生成或刚读过，原始文件几乎一定在系统文件缓存里；要做真正的“冷读”需要管理员权限清空备用列表，本次**未测量**。因此“冷”指的是**应用自己的缓存冷**，不是磁盘冷。Shell 路线的冷／热通过改夹具的修改时间（thumbcache 键含修改时间）来制造；用户自己的目录绝不改动。

### 2.4 数据集

夹具全部由程序生成在 `%TEMP%\sfm-thumbs`（可丢弃，不入库）：

| 夹具 | 内容 |
| --- | --- |

| `mixed` | 60 个文件，其中 6 个异常（截断、零长度、PNG 冒充 .webp、1.44 亿像素、带 RIFF 头的垃圾、正文翻转位），清单在 `mixed-manifest.json` |

### 2.5 匿名公开记录

结果 JSON 与 `logs/` 日志只含数值和类别（`io`／`corrupt`／`unsupported`／`too_large`／`timeout`），**不含路径、文件名、图像内容**。`-Dir` 只读你的目录：不写缓存到该目录、不改时间戳；缩略图缓存写在 `%TEMP%\sfm-thumbs\cache-*`。沿用现有日志约定（`logs\yyyy-MM-dd HH-mm-ss.log`）和 `scripts/perf-browse.ps1`、`src/perf.rs`，没有新建日志模块。

## 3. 路线对比（256 px，单线程，每条路线一个独立进程）

`webp-photo-60`，60 张，平均 11.8 MP。内存是峰值已提交内存（`PeakPagefileUsage`）相对启动时的增量，只含本进程。

| 路线 | 每张中位 | p90 | 峰值内存增量 | 说明 |
| --- | --- | --- | --- | --- |
| libwebp 解码时缩放（`libwebp-scaled`） | 18.7 ms | 22.2 ms | 1.2 MiB | 读取约 0.13 ms，其余是解码＋缩放（不可分） |
| libwebp 缩放＋跳过滤波与精细上采样（`libwebp-fast`） | 18.8 ms | 21.7 ms | 1.2 MiB | 与上一行几乎无差别，画质指标也相同 |
| libwebp 整幅解码 + `fast_image_resize` 双线性（`libwebp-full`） | 36.2 ms | 40.1 ms | 50.7 MiB | 整幅 RGBA 先分配 |
| 纯 Rust：`image`（`image-webp`）+ `fast_image_resize`（`rust-image`） | 129.5 ms | 135.8 ms | 82.7 MiB | |
| Windows Shell，冷（`shell-cold`） | 112.9 ms | 119.0 ms | 2.9 MiB（仅本进程；Shell 的解码在进程外，未测量） | 每个文件都要先让系统生成 |
| Windows Shell，热（`shell-hot`） | 3.7 ms | 3.9 ms | — | 命中系统 thumbcache |
| Windows Shell，冷，4 线程 | 119.5 ms | 419.1 ms | 4.4 MiB | 吞吐 9.4 张/s（单线程 8.8 张/s）；单张均值 416 ms，最长 6.4 s |

样本量：每条路线跑一遍 60 张（路线表的“每条路线重复 1 次”，没有置信区间）。Shell 并发另外补测：1 线程 8.9／8.8 张/s（两次），2 线程 9.3 张/s，4 线程 9.2／9.4 张/s（又两次，加上表里的一次共 3 次），说明 Shell 提取串行，不是偶发抖动。4 线程每次的单张最长都约等于总时长（6.4～6.5 s），说明有一个请求被排到最后；原因没有深查。

分段（解码／缩放）：`libwebp-scaled` 的缩放在解码里完成，所以只有“读取 + 解码（含缩放）”；整幅解码路线才能分出缩放这一段。Shell 不可分段。

**体积不能推断耗时**：同分辨率、体积约大 18 倍的细节密集 WebP（`webp-dense-12`）：

| 路线 | 每张中位 |
| --- | --- |
| libwebp（fast） | 136.0 ms（对比平滑 WebP 的 18.8 ms，慢 7 倍） |
| `rust-image` | 273.6 ms |
| Shell 冷 | 233.5 ms（p90 245.4 ms） |

**其他格式**（每种一张 1200 万像素，GIF 300 万，各路线一个进程）：

| 格式 | `rust-image` 中位／峰值内存增量 | Shell 冷 |
| --- | --- | --- |
| JPEG | 30.3 ms／81.5 MiB | 68.0 ms |
| PNG | 58.5 ms／96.2 MiB | 156.0 ms |
| BMP | 42.7 ms／115.0 MiB | 70.7 ms |
| GIF（300 万） | 11.6 ms／25.2 MiB | 60.1 ms |

**超大尺寸**：1.44 亿像素 WebP（文件只有约 0.4 MB），关闭像素上限后：

| 路线 | 耗时 | 峰值内存增量 |
| --- | --- | --- |
| libwebp 缩放 | 119.8 ms | 1.8 MiB |
| libwebp 整幅 | 307.5 ms | 563.3 MiB |
| `rust-image` | 1018.2 ms | 964.2 MiB |

整幅解码路线的内存约是每像素 4～7 字节（`rust-image` 在 1.44 亿像素上是 964 MiB，约 6.7 MiB／百万像素），4 个工作线程同时遇到大图就是数百 MiB 到 GiB 量级。这决定了第 6 节的像素上限。

**WebP 变体**（同一幅 1200 万像素图，重复 3 次取中位，单线程）。这一节是复核时发现“缩放解码省内存”只对有损不透明成立后补测的：

| 变体（源文件大小） | libwebp 缩放 | libwebp 整幅 | `rust-image` |
| --- | --- | --- | --- |
| 有损不透明（平均约 201 KiB，见上表） | 18.7 ms／+1.2 MiB | 36.2 ms／+50.7 MiB | 129.5 ms／+82.7 MiB |
| 有损带透明（314 KiB） | 39.7 ms／+70.4 MiB | 72.0 ms／+116.3 MiB | 155.3 ms／+121.2 MiB |
| 无损（7.5 MiB） | 91.6 ms／+54.6 MiB | 97.2 ms／+100.4 MiB | 113.5 ms／+88.6 MiB |

带透明或无损时，libwebp 的缩放仍要分配整幅缓冲，内存约每百万像素 4.8～6.2 MiB（缩放只省掉一份副本）；无损的解码时间也几乎没有缩放收益。“有损不透明”变体的数字来自表中第一行的另一次运行，不是同一次。这三个变体各只有一张图，不代表真实照片。

**画质与透明**（256 px，6 张，以“libwebp 整幅 + `fast_image_resize` 双线性”为参照）：

| 路线 | MAE（0～255） | PSNR |
| --- | --- | --- |
| libwebp 缩放／fast | 0.34 | 52.6 dB |
| `rust-image` | 0.00 | 与参照逐像素一致 |
| Shell | 0.87 | 46.5 dB |

注意：`rust-image` 的 0.00 是**循环参照**——参照和它用的是同一个缩放器、同一份解码结果，只能说明 `image-webp` 的解码与 libwebp 一致，不能说明缩放画质。参照本身也不是“真值”，只有 6 张平滑合成图，**没有目视对比，只有数值**，所以不要据此断言画质相同。透明 WebP：5 条路线都保留了 alpha（中心 alpha = 0，四角 255），Shell 路线已从预乘还原为非预乘。

## 4. 调度链路实测（可见优先、滚动取消、慢文件隔离）

原型 `pipeline.rs` 实现了这条链路，三个单元测试覆盖语义（滚动后不再启动过期任务、旧 epoch 结果带 epoch、慢文件既不阻塞其他也不永久挂起），下面是在 `webp-photo-60`／`mixed` 上的场景实测（4 工作线程，首屏 28，预取 28，硬超时 2 s，`slow_after` 300 ms，最多增援 4 个线程）。

| 场景 | 结果 |
| --- | --- |
| 滚动（用 `many-600`：`webp-photo-60` 的 10 份硬链接，共 600 个路径；40 ms 后一次跳到第 300 项） | 排队中取消 41 个；在途无法取消 4 个（只能丢弃结果）；滚动之后才开始的视口外任务 **0** 个；新首屏 105 ms 内 28／28 齐全。**这个 105 ms 不能和第 5 节的 178 ms 比**：本场景解码中位 13 ms，其他场景 22 ms，原因没有查清（同样的图、同样的 4 线程），只把计数结果当作语义验证 |
| 换目录 | 旧 epoch 的结果丢弃 4 个；绑定错位（key 对不上）**0** 个 |
| 1 个慢文件（注入 2.6 s，硬超时 2 s） | 其余首屏 216.7 ms 齐全（比正常多约 38 ms：慢文件占住一个线程，300 ms 后才增援）；慢项在 2.0 s 显示回退图标（`timeout`），2.6 s 迟到成功后补上（`ready_late`） |
| 4 个同时慢（占满全部线程） | 其余首屏 458.4 ms 齐全（要等 300 ms 增援线程拉起来） |
| 60 个文件含 6 个异常 | 成功 55；失败 `corrupt` 4、`too_large` 1；没有崩溃或挂起。PNG 冒充 .webp 的文件按内容识别后解码成功 |

注意：

- **在途解码不能中断**（libwebp 一次 `WebPDecode` 调用没有取消点），所以“取消”实际是“排队的不再开始、在途的结果标记为视口外或丢弃”。大图被取消后仍会白占一个线程到解码结束；兜底靠第 6.3 节的像素上限和硬超时，没有做更强的取消。
- 无头原型的“界面线程”只做绑定核对，耗时极小（两次调用共 16 µs）。**Slint 的图像上传与渲染不在内**，所以这里的首屏时间是**下界**，不是整机 UI 成绩。
- 迟到成功的结果仍要经过 epoch／key 核对后才绑定，原型里 `late` 标记就是为此保留。

## 5. 冷／热／重启（首屏 28 项，4 线程，重复 5 次，无头）

| 磁盘缓存格式 | 冷（中位／最大） | 同进程热 | 重启后 | 磁盘缓存 |
| --- | --- | --- | --- | --- |
| 有损 WebP q80 | 186.0 ms／191.5 ms | 0.02 ms | 2.32 ms（最大 2.56 ms） | 56 项，69,296 字节 |
| 原始 RGBA | 173.9 ms／176.2 ms | 0.02 ms | 1.61 ms（最大 1.68 ms） | 56 项，10,853,824 字节 |
| 无磁盘缓存 | 176.1 ms | 0.02 ms（内存） | 不适用 | — |

- “56 项”是首屏 28 加预取 28。
- 有损 WebP 缓存比原始 RGBA 慢约 0.7 ms（28 项重启），体积小得多；但合成图像平滑，**缩略图缓存体积偏小**（平均约 1.2 KB／张），真实照片的 q80 缩略图预计大得多（约几十 KB 以内，**未测量**）。因此 #10 应在真实目录上复测缓存体积再定磁盘配额。
- 进程内内存缓存里是未压缩 RGBA（256×192×4 ≈ 192 KiB／张）。56 项的峰值已提交内存比启动时多约 14 MiB。**内存缓存必须设上限**（例如 128 MiB ≈ 680 张，按 192 KiB 计算），具体值由 #10 定。

## 6. 选定路线、失败与超时策略

### 6.1 路线

| 格式 | 路线 | 状态 |
| --- | --- | --- |
| WebP（静态，有损不透明） | libwebp 解码时缩放 | 已验证，选定（合成图） |
| WebP（静态，无损或带透明） | 同样用 libwebp 缩放，但内存和耗时优势很小，要像素上限 | 已测一张，见第 3 节变体表 |
| JPEG／PNG／BMP／GIF（首帧） | Rust `image` 整幅解码 + `fast_image_resize` | 已测速度和内存，建议；JPEG 未测“解码时缩放”或 EXIF 内嵌缩略图 |
| 动画 WebP、GIF 动图 | 原型对动画 WebP 返回 `unsupported`（显示图标），GIF 取首帧 | 代表帧未验证 |
| 视频、HEIC、PDF、Office 等 | Windows Shell，最多 1～2 个并发 | 只测了 Shell 对图片的耗时，这些格式本身**未覆盖** |
| 云占位文件（仅在线） | Shell `SIIGBF_INCACHEONLY\|THUMBNAILONLY`，失败回退图标，绝不读取内容 | 依据 0003，本次未复测 |

按内容识别格式（看 RIFF/WEBP 头，不看扩展名），PNG 冒充 .webp 的文件解码成功。

### 6.2 失败与超时策略（原型采用并验证）

- 读头之后先做限制检查，**超限不解码**：像素超限或文件体积超限返回 `too_large`，界面显示类型图标。
- 失败类别只有五种：`io`、`corrupt`、`unsupported`、`too_large`、`timeout`。全部回退到类型图标，不重试，不弹错误提示；只在日志里记类别。
- 慢文件：300 ms 未返回 → 临时增援一个线程（最多 4 个），避免一个慢文件堵住队列。
- 硬超时：2 s 未返回 → 该项显示回退图标并结束等待；之后若解码成功，**仍然补上**（带 epoch／key 核对）。
- 目录切换：epoch 自增，旧结果直接丢弃。

### 6.3 像素与内存上限（建议）

先用 `WebPGetFeatures` 读头（格式：有损／无损、是否带透明、是否动画、宽高），再决定：

- **有损且不透明的 WebP**：libwebp 缩放路线不需要像素上限，1.44 亿像素只要 1.8 MiB（实测）；WebP 本身最大 16383×16383（约 2.7 亿像素）。保留硬超时即可。原型当前对所有路线用同一个 1.2 亿像素上限，所以会拒绝这张 1.44 亿像素的有损 WebP——对这一类是**过严**的。
- **无损或带透明的 WebP**：缩放也要分配整幅缓冲（第 3 节变体表：每百万像素 4.8～6.2 MiB）。必须设上限。建议 2400 万像素（按 6.2 MiB／百万像素约 150 MiB／张，**推算值，未实测大图**），超限显示图标。
- **整幅解码路线（`image`：JPEG／PNG／BMP／GIF）**：必须设上限。按实测 6.7 MiB／百万像素（1.44 亿像素 964 MiB）推算，建议同样 2400 万像素以内（约 160 MiB／张，推算值）。4 个工作线程同时遇到大图时最坏约 4 倍，所以建议大图（超过 1200 万像素）限制并发 1～2 个，具体由 #10 定。
- 文件体积上限：256 MiB（原型默认），读取前检查。

以上上限是对**内存**的保护；耗时靠硬超时兜底。无损大图的耗时随像素线性增长（1200 万像素约 92 ms），首屏全是无损图时，28 张 4 线程估算约 0.64 s（由 92 ms ×28 ÷ 4 推算，**未实测**）。

## 7. 未覆盖与已知局限

- **Windows 11**：无环境，未验证（Shell 路线尤其需要确认 WebP 缩略图提取器是否安装）。
- **操作系统文件缓存冷态**：未控制，未测量（需要管理员权限清备用列表）。真正第一次读盘的首屏时间会比表里更长，NVMe 下差距预计较小，但**没有数据**。
- **整机 UI 成绩**：原型无头，不含 Slint 上传与渲染，也不含窗口合成。首屏缩略图的整机时间在产品实现之前是“未测量”。
- **真实照片**：合成夹具平滑，缩略图体积偏小；真实照片解码耗时可能偏离（见 `webp-dense-12`）。
- **其他机器**：只在一台 6 核／12 线程机器上测。弱 CPU（4 核以下）的线程数和首屏时间会偏离，没有数据。
- **未覆盖格式**：动画 WebP／GIF 的代表帧、HEIC、视频、PDF、Office、RAW、EXIF 方向（旋转）、色彩管理（ICC）。
- **Shell 进程外内存**：Shell 路线的解码发生在进程外，原型只测了本进程内存。
- **极大目录**：没有测 1000～10000 个文件目录下的预取与内存缓存淘汰（调度只做了 60 个文件的场景，`many-600` 夹具只生成未跑场景）。
- **未评估的备选路线**：JPEG 的 DCT 域缩放（libjpeg-turbo）和 EXIF 内嵌缩略图、WIC 解码器（带缩放）、WIC／Shell 混合。这次没有比较它们，所以“JPEG／PNG 用 `image`”只是“能用、速度可接受”，不是“最优”。
- **样本量**：路线对比每条路线 1 次（60 张），格式对比 `rust-image` 3 次、Shell 1 次，线程扫描 3 次，冷／热／重启 5 个进程，产品“可操作”冷首次和重启首次各只有 1 个样本（n=1）。没有置信区间，小差异（例如 libwebp fast 与 scaled 的 0.1 ms）不要当作结论。
- **机器负载**：本机同时还有别的编译任务在跑时，同一份脚本的数字会明显变慢。例如一次 `-Quick` 试跑（后台有编译）里，28 项冷首屏是 440～787 ms，空闲时是 174～186 ms；路线对比里每张耗时也慢了 1.1～2 倍。本文数字取自较空闲的一次完整运行（与更早一次完整运行相比大多在 10% 以内），但**没有监测负载**，脚本只在开头记录一次 CPU 负载（`env.cpu_load_pct_at_start`），基线要在空闲机器上采集，对比前后数据必须看这个值。
- **内存口径**：只有本进程峰值已提交内存，且是单线程数字；多线程要乘以并发数。Shell 在进程外的内存没测。
- **调度没覆盖的场景**：连续滚动、来回滚动、快速连续换目录（只测了一次跳转）；真实阻塞 I/O（网络盘、云占位、杀毒扫描，慢文件是 `sleep` 注入）；基础线程加增援线程全部卡死（8 个）；硬超时后迟到补图时用户已滚走；在途大图占用线程对后续项的影响；“可见优先”只用计数间接证明，没有记录实际启动顺序。
- **用户自己的目录**：脚本支持 `-Dir`（已用合成目录当作“自己的目录”跑通，只含统计），但本记录的数字全部来自合成数据；真实目录的结果由使用者自行运行。`-Dir` 模式不改你的时间戳，所以 Shell 路线的“冷”其实是系统 thumbcache 的当前状态（试跑里每张约 5.7 ms，与热态相同），不是冷态，也不跑异常文件和慢文件注入。
- **目视检查**：缩略图画质只有数值指标，没有目视对比。

## 8. 给 #10 的契约

1. **产品事件**：`thumbs-first-screen-us`（单个整数，微秒，起点与 `dir-ready-us` 相同；终点是首屏正常项全部绘制缩略图的第一帧）。事件只含一个整数，符合 `src/perf.rs` 的“静态字符串＋一个整数”约定，天然匿名。另外建议分别记失败／超时项数量（同样用静态字符串＋整数，不含路径）。
2. **缓存目录**：环境变量 `SFM_THUMB_CACHE_DIR` 指定磁盘缓存目录。冷 = 清空该目录，重启 = 保留目录并启动新进程，同进程热 = `--bench-enter` 的第 2 次起。`scripts/perf-thumbs.ps1` 已按这个约定解析日志，事件不存在时显示“未测量”。
3. **计时挂钩要小而集中**：只在“发起进入目录”和“首屏缩略图全部绘制完成”两点记时，不要把计时散落在 `src/app/`、`src/browse/`、`ui/` 各处。
4. **照搬的接口形状**：每个结果带 `(epoch, index, key)`；`set_viewport(first, last)` 只重排队列（可见 → 预取前方 → 预取后方），已排队的取消，在途的丢弃；增援线程与硬超时放在一个 watchdog 里。参考 `prototypes/thumb-probe/src/pipeline.rs`。
5. **复测**：实现后运行 `powershell -File scripts/perf-thumbs.ps1`，产品部分会自动出现首屏缩略图的冷／热／重启数据，再与第 1 节的目标对照。
