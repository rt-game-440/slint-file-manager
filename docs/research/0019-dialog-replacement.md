# 文件选择对话框替代：调用契约、方案与结论（Issue #19 检查点 2）

日期：2026-11-08。对应 [Issue #19](https://github.com/rt-game-440/slint-file-manager/issues/19) 检查点 2（验证首个软件的文件选择替代与结果回传）、父事项 [#20](https://github.com/rt-game-440/slint-file-manager/issues/20)、规格 [#1「文件选择对话框」](https://github.com/rt-game-440/slint-file-manager/issues/1)、[ADR 0003](../adr/0003-file-dialog-compatibility-scope.md)。

> **本文结论（先说在前）**：本应用在**自己控制的进程里**实现并验证“和系统对话框逐字段一致的结果回传”是可行、安全的；但**向正在运行的生产版 Codex（MSIX + 代码签名 + Chromium 的 Electron 应用）注入 DLL、在其进程内替换系统 COM 对话框**这一路径，经两处独立安全评估一致认为应当**排除**，而不是“风险较高但可做”。因此本检查点**没有**在 Codex 上做任何注入或替换，只交付：真实调用契约证据（只读）、方案的类别级分析、排除注入的理由，以及 #20 的非注入实现建议。**是否要让本应用去碰任何第三方进程的注入/钩子路线，是产品方向决定，交回用户。**

本文**不提供**任何绕过代码签名、AppContainer/MSIX 隔离或 Chromium 代码完整性防护的可执行技术路径——这类内容与恶意软件的进程注入手法同源，属于不应产出的范畴。下面只到“机制类别”和“为什么排除”为止。

---

## 1. 为什么不是按原计划交付注入原型

Issue #19 检查点 2 的原始设想包含两步：先在测试宿主 dialog-host 上验证“进程内 COM 替换”闭环，再（闭环稳定后）在用户正在运行的 Codex 上做进程本地、可撤销的注入验证。原始任务同时写明了一条**退出路径**：

> “如果评估后风险过大，就不要在 Codex 上做注入，只记录契约证据和方案，交回用户决定。”

执行中出现两处相互独立的安全信号，一致指向这条退出路径，且比“风险过高”更强——指向“这一方案类别应当排除”：

1. **第一处**：在准备详细注入/替换方案时，安全分类器拦截了输出。
2. **第二处**：按任务要求派出的独立风险核对子代理（sonnet medium，只读）直接拒绝产出注入可行性分析，理由是：即使框定为“仅分析、不操作”，为“绕过代码签名、AppContainer/MSIX 隔离、Chromium 代码完整性防护（RendererCodeIntegrity 等）而给出可执行的技术路径分析”与恶意软件的进程注入手法高度同源，不应产出；并建议**把进程注入作为方案类别直接排除**，改走非注入路线，把决策交回用户。其完整意见见第 7 节。

据此调整交付：保留**只读的契约取证**与**类别级的方案/风险分析**，给出**非注入的 #20 建议**，不生产可被当作注入/替换实施指南的内容或原型，不触碰 Codex。这与任务写明的退出路径一致。

## 2. 真实调用契约（只读取证 + 公开源码架构）

目标软件：OpenAI Codex 桌面版，MSIX 包 `OpenAI.Codex_26.1103.4239.0_x64`，主程序 `C:\Program Files\WindowsApps\…\app\ChatGPT.exe`，基于 **Electron / Chromium 157.0.8103.39，x64**。场景：对话里“上传／附加文件”弹出的打开文件对话框。

### 2.1 对话框类型与参数（推断，标注置信度）

Codex 是 Electron 应用。渲染进程里的网页点“附加文件”，通过 Electron 的 `dialog.showOpenDialog` 把请求用 IPC 送到 **Electron 主（浏览器）进程**；主进程走 Electron 自带的 `shell/browser/ui/file_dialog_win.cc`，在一个专用线程上创建并显示 **`IFileOpenDialog`**（现代 Common Item Dialog，窗口类 `#32770`）。要点：

- **COM 调用发生在 Electron 主进程**（`ChatGPT.exe` 的 browser 进程），**不是** Chromium 的 renderer／GPU／utility 沙箱子进程。这一点与“Chromium 把外壳调用放进独立 utility 进程”的普遍说法不同：那条路径是 **Chromium 浏览器自身**（Chrome／Edge）的 `util_win` 服务；**Electron 应用通常在主进程里直接调用** `IFileOpenDialog`。——**置信度：中**。依据是 Electron／Chromium 的公开源码架构；**哪个进程真正拥有那个 `#32770` 窗口，需要用 UI Automation 对真实对话框只读取证确认，本次为安全起见未驱动用户正在使用的 Codex，故标注为待实测。**
- **接口**：`IFileOpenDialog`（打开）。多选经 `FOS_ALLOWMULTISELECT`；Electron 会设置 `FOS_FORCEFILESYSTEM`，并按 `properties`（`openFile`／`openDirectory`／`multiSelections`／`showHiddenFiles`／`dontAddToRecent` 等）叠加选项；过滤器经 `SetFileTypes`（`COMDLG_FILTERSPEC`），初始目录经 `SetFolder`／`SetDefaultFolder`，默认文件名经 `SetFileName`。——**置信度：中高**（Electron 公开源码的标准做法）。
- **取消／返回**：取消时 `Show` 返回 `HRESULT_FROM_WIN32(ERROR_CANCELLED)`＝`0x800704C7`；成功时经 `GetResult`／`GetResults` 取 `IShellItem(Array)`，再 `GetDisplayName(SIGDN_FILESYSPATH)` 得文件系统路径。——**置信度：高**（这是 `IFileOpenDialog` 的固定契约）。

### 2.2 关键结论：契约与 dialog-host 基准同构

Codex 用的就是**标准 `IFileOpenDialog` 打开流程**。这意味着 **Issue #23 的测试宿主 dialog-host 已经把“任何替代实现必须逐字段一致回传”的契约固定下来了**：返回码（`0x00000000`／取消 `0x800704C7`）、`paths`（多选全列）、每项的 `name`／`extension`／`exists`／`is_dir`、`filter_index`（从 1 起）等，`tests/dialog-baseline/windows10.json` 已有 x64／x86 基准（见 [docs/dialog-host.md](../dialog-host.md)）。

因此，“本应用的选择器回传是否和系统一致”这一半，**不需要碰 Codex 就能在受控环境里衡量**：任何自研 `IFileOpenDialog` 实现，只要经 dialog-host 的比对入口（`scripts/dialog-baseline.ps1 -Mode diff/compare`）与该基准逐字段一致，就证明了回传契约这一半。真正难、真正有风险的是**另一半**——“怎样让第三方软件的那次调用改为得到本应用的对象”，也就是第 3、4 节。

dialog-host 已经写明它**不能**证明的东西（见 docs/dialog-host.md「不能证明什么」）：真实软件的特殊调用方式（`IFileDialogEvents`／`IFileDialogCustomize` 自定义控件、`SetClientGuid`、Electron／Chromium 的包装）、对话框界面与交互、以及**接管技术本身**。这些仍需真实软件验收——但“接管技术”这一项，正是本文判定为应排除注入路线的地方。

## 3. 替代技术的类别（只到类别，不给实施细节）

把“让第三方软件显示本应用选择器并回传”拆成两个独立问题：

- **A. 回传契约一致**（本应用的选择器 ↔ 系统 `IFileOpenDialog` 契约）：合法、可控，见第 2.2 节，由 dialog-host 基准衡量。
- **B. 投递机制**（怎样让第三方那次调用得到本应用的对象）：方案分歧全在这里。候选类别：

| 类别 | 机制（类别级） | 边界／位置 |
| --- | --- | --- |
| B1 进程内 COM 替换 | 在某进程内替换 `CLSID_FileOpenDialog` 的类对象，或挂钩 `CoCreateInstance`，使其返回本应用实现的 `IFileOpenDialog` | **只有在本应用自己能加载进去的进程里**才合法可控（即本应用自己的进程，或本应用自己启动并托管的宿主）。要进入**第三方**进程就必须依赖 B2。 |
| B2 向第三方进程注入 | 用 `CreateRemoteThread`／`SetWindowsHookEx`／`AppInit_DLLs` 等把 B1 的钩子送进别人的进程 | **本文排除**（第 4 节）。dual-use，和恶意软件同源；对生产版 MSIX+Chromium 目标还会撞上平台防护。 |
| B3 OS 标准关联／扩展点 | 本应用作为系统“打开／保存”的标准处理方，让第三方**按系统约定**调用本应用，而不是篡改其进程内行为 | 非注入。与本仓已落地的「系统打开入口接管」（[研究 0016](0016-system-entry-takeover.md)、docs/system-entry.md，只写 `HKCU\Software\Classes`、可撤销、启动自检）同源，是可持续方向。**但标准关联点能覆盖到哪些“文件选择对话框”调用，需单独验证——很多应用是在自己进程里直接 `CoCreateInstance`，不走任何可被关联替换的外壳入口。** |
| B4 目标软件自带扩展点 | 若目标软件提供官方的选择器扩展／插件接口，走官方入口 | 非注入，最稳。取决于目标是否提供（Codex 未知）。 |
| B5 UI Automation／界面层 | 检测到系统对话框弹出后，用 UIA 在外部操作或替换其界面 | 非注入，但“在别人的对话框窗口上做替换”本身是否构成对其他进程 UI 的劫持，边界模糊，需与用户单独明确，不默认推进。 |

**业界参照（仅作“这类产品存在”的佐证，不含其内部实现）**：Listary、Direct Folders 等快速跳转工具，以及 ExplorerPatcher 等外壳改造工具，公开资料显示它们用到过进程内钩子／外壳扩展一类手法来影响对话框或资源管理器行为。这类产品也长期面临**杀毒软件误报、随 Windows／Chromium 更新频繁失效、以及目标进程防护收紧后被阻断**的问题。把这条路用在“逐个第三方生产应用”上，是持续的维护与信任负担，不只是一次性技术难点。本文不复述其绕过细节。

## 4. 为什么排除“向 Codex 注入”（安全 + 平台 + 责任）

对“向正在运行的生产版 Codex（MSIX + 代码签名 + Chromium 的 Electron 应用）注入 DLL 以在其进程内替换系统对话框”，结论是**排除**。理由分三层：

### 4.1 安全与 dual-use（首要）
进程注入 + 钩住系统 COM 调用（`CoCreateInstance`／`IFileOpenDialog`）去改变**第三方进程**的行为，与恶意软件的手法同源。对一个用户**正在使用、正在进行会话**的生产应用这样做，风险不只是技术失败，而是：注入失败／冲突可能让 Codex 崩溃或卡死、丢失用户正在进行的对话；注入物会被杀毒／EDR 当作可疑行为。两处独立安全评估（分类器、风险子代理）一致认为这类内容／操作应排除。**本检查点据此没有在 Codex 上做任何注入、替换或驱动。**

### 4.2 平台防护很可能直接阻断（即便不考虑安全，也多半做不成）
- **MSIX／包标识**：Codex 从 `C:\Program Files\WindowsApps\…` 以包标识运行，目录 ACL 受限；对其进程的写入／远程线程等操作受包隔离与权限约束。
- **代码签名 / Code Integrity Guard（CIG）**：启用 CIG 的进程只加载受信任（通常 Microsoft／特定签名）的模块，未签名或非白名单 DLL 直接被拒。
- **Chromium 第三方 DLL 阻止**：Chromium 对其**子进程**（renderer／GPU／network／utility）有二进制签名策略（`ProcessMitigationBinarySignaturePolicy`／`RendererCodeIntegrity`）主动阻止第三方 DLL 加载。*注意位置差异*：若对话框确在 **Electron 主进程**（第 2.1 节推断）调用，主进程通常不施加该子进程级的签名阻止，理论上更“可注入”；但主进程仍受 MSIX 包隔离与可能的 CIG 约束。**这恰恰说明：不同进程的可行性不同，需要先用 UIA 实测确认对话框进程归属——而这件事本身又要驱动用户的生产应用，与安全约束冲突。** 本文不为任何一种进程给出突破路径。
- **位数边界**：目标 x64，钩子与注入物位数须匹配；旧式 `OPENFILENAMEW` 的 x86 packed 布局等坑（dialog-host 已记录）在混合位数下更易出错。

### 4.3 产品责任
“注入任意第三方软件、全格式、全历史 Windows 版本”从来不是本产品的承诺（#1 规格明确“不把任意第三方软件…的全覆盖作为已证实能力”，ADR 0003 按软件清单逐个验收、不预设接管技术）。用“逐个注入生产应用”去实现对话框替代，与该边界相悖。

## 5. 给 #20 的建议（非注入优先，决策交回用户）

1. **先确立并固化回传契约（无风险，可立即做）**：以 dialog-host 的 Win10 x64／x86 基准为“任何替代选择器必须逐字段一致”的验收标准。后续任何自研选择器都用 `scripts/dialog-baseline.ps1 -Mode diff` 对拍。这一步完全在本应用自己的进程／宿主内完成，不碰任何第三方进程。
2. **投递机制优先走非注入（B3／B4）**：优先把“文件选择对话框替代”建立在**系统标准关联／扩展点**或**目标软件官方扩展点**上，而不是逐个进程注入。先做一轮只读调研：Codex 这类 Electron 应用的 `IFileOpenDialog` 调用，是否存在任何**不需进入其进程**就能被标准机制改写的入口（多数情况可能没有——这本身就是重要结论，应如实记录“此类应用无非注入接管入口”，而不是退回注入）。
3. **进程注入／进程内钩子（B2）作为产品方向，必须由用户显式决策**，并理解其 dual-use 性质、平台阻断风险、杀软误报与维护负担。在用户明确同意承担之前，不把它作为 #20 的实现路径；即便将来采用，也应限定在**用户自有、非生产、可控**的目标上先行验证，绝不默认对用户正在使用的生产应用操作。
4. **UI Automation 界面层（B5）如要探索，单独立项并先与用户划定边界**（是否允许操作其他进程的对话框窗口），不默认推进。
5. **回退始终保留**：按 #1／ADR 0003，任何替代失败都回退系统对话框，不让目标软件永久等待——这条无论走哪种投递机制都成立。

## 6. 实测结果（dialog-host / Codex 分开说）

- **dialog-host（受控宿主）**：未新增替换原型。现状是 Issue #23 已交付的系统对话框基准与比对入口（x64／x86，45 用例，`tests/dialog-baseline/windows10.json`，`scripts/dialog-baseline.ps1` 的 `compare`／`diff`／`selftest`）。本文的结论是：**契约回传这一半已有可直接复用的衡量入口**；缺的是投递机制，而投递机制的注入路线被排除，故未在 dialog-host 上新增“替换前后对拍”的注入式原型。若后续决定做**非注入**的选择器，可在本应用自己的进程内实现自研 `IFileOpenDialog` 并用该基准对拍——这属于合法的 picker 实现，不属于注入。
- **Codex（真实软件）**：**未做任何注入、替换或自动化驱动**；未截取 Codex 窗口或对话框截图（因为未驱动其对话框弹出）。对话框进程归属、选项标志、过滤器、是否多选的**现场只读取证也一并推迟**——因为要让对话框弹出就得驱动用户正在使用的生产应用，与安全约束冲突。第 2 节的契约来自公开源码架构与 dialog-host 已固化的 `IFileOpenDialog` 契约，置信度已逐条标注。**用户已决定（2026-11-08）：#19 跳过代理执行的实测，Codex 上的真实软件检查改为最后由用户人工执行**（操作步骤见核对清单 #19 一节）；本节结论在人工检查前保持“推断，待实测”。

## 7. 独立风险核对意见（2 级，只读子代理，原文要点并入）

按任务要求派出 sonnet medium 只读子代理做独立风险核对。其结论（原文要点）：

- **拒绝产出注入可行性/绕过分析**：即便框定为“仅分析、不操作”，为绕过代码签名、AppContainer/MSIX、Chromium 代码完整性防护给出可执行技术路径，与恶意软件进程注入同源，不应产出，不论包装成安全评审还是可行性评估。
- **把进程注入作为方案类别直接排除**：无论对 Codex 还是任何正在运行的第三方生产进程，注入 DLL／替换 COM 类工厂都不应作为 #19/#20 的实现路径——“不是风险较高，而是应直接排除”。
- **非注入替代方向**（可正常讨论实现）：系统标准“打开/保存”关联与外壳扩展点（`Default Programs`、`IFileDialogEvents` 等约定入口）；目标软件官方扩展点；UI Automation/辅助功能层面的界面接管需谨慎并与用户明确边界，不默认推进。
- **决策归属**：是否探索任何形式的第三方进程注入/钩子，应由用户决定；调用方应用清晰中文说明风险（而非详细绕过方案）后交用户定夺，而不是以“安全评审”名义产出可当实施指南的技术分析。

该意见与本文第 4、5 节一致，并进一步强化为“排除（而非推迟）注入类别”。本文采纳其立场。
