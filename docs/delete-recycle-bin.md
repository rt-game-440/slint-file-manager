# 删除、回收站浏览与还原（Issue #8）

## 用户可见行为

- **入口**：Delete 与工具栏“删除”= 移到回收站；Shift+Delete 与工具栏红色“永久删除”= 永久删除。两者都先弹应用内确认框（见 ADR 0006：进度、冲突、权限提示允许使用系统界面，确认框是应用自己的）。
  - 移到回收站的确认：Enter 确定、Esc 取消。
  - 永久删除的确认：红色标题与主按钮，**Enter 无效**，必须点按钮；Esc 取消。默认动作永远是更安全的取消。
  - 取消不改变任何文件，状态栏提示“已取消，没有删除任何项目”。
- **不静默退化**：所在位置不支持回收站（可移动磁盘、网络位置、路径超过 260 字符）时：全部不支持则只弹说明“无法移到回收站”，不执行任何操作；部分不支持则确认框写明这些项目不会被删除也不会被永久删除，执行后它们保持原样并在汇报里点名。系统在回收时若想改为永久删除，会先询问（`FOF_WANTNUKEWARNING`），被拒绝按“操作被取消”处理。
- **如实汇报**：逐项执行并逐项记录结果。全部成功只写状态栏一行（“已将 N 项移到回收站”）；有失败时状态栏为红色“部分完成：K 项已…，M 项未能…”，并弹说明框列出（最多 8 个）失败项与原因（没有权限、正被其他程序使用、项目已不存在、同名未覆盖、原文件夹已不存在、此位置不支持回收站）。列表刷新不代表成功：失败项仍在原处，列表里继续显示。
- **回收站视图**：侧栏“回收站”进入，地址栏显示“回收站”，顶部米黄色提示条说明“不是普通文件夹”，列为名称／删除日期／原位置／大小（固定列表视图；点“原位置”表头按原位置排序）。双击不打开，提示先还原；Delete 与工具栏删除在这里不可用；**没有清空回收站入口**。
- **还原**：选中后点“还原所选项目”，不需要确认（它不破坏任何东西）。还原到原位置；同名冲突不覆盖、原文件夹不存在不自动重建、权限不足——这三类都让项目留在回收站并汇报原因。成功后回收站视图与所有显示原目录的标签立即更新。

## 结构

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 接口与汇报 | `src/fileops.rs` | `Backend` trait（回收、永久删除、枚举回收站、还原，每次一个项目）；`run_delete`／`run_restore` 逐项执行并生成 `Report`；`Summary` 汇报措辞；`StashBackend`（临时目录“回收站”，可注入失败，harness 与测试用） |
| Windows 实现 | `src/recycle.rs` | 外壳命名空间枚举与还原、`SHFileOperationW` 回收、`can_recycle` 静态判断 |
| 界面接线 | `src/app/ops.rs` | 确认框状态机、后台线程执行、完成后刷新受影响标签并汇报 |
| 浏览模型 | `src/browse/{location,tab,entry,workspace}.rs` | 回收站虚拟位置 `shell:RecycleBinFolder`、`Entry.bin`（项目标识与原位置）、`Workspace::refresh_where` |
| 界面 | `ui/dialog.slint` 等 | `ModalDialog`、回收站提示条、工具栏按钮 |

### 回收站不是普通路径

回收站用 `FOLDERID_RecycleBinFolder` 的 `IShellFolder2` 枚举（所有磁盘的合并视图，与资源管理器一致），名称／原位置／删除时间／大小来自外壳属性。项目标识是外壳相对 PIDL 的字节拷贝，还原时原样交回；绝不拼出 `$Recycle.Bin` 路径去当普通目录读。还原走外壳自己的 `undelete` 命令（与资源管理器“还原”同路径、同时清理元数据）。

三个必须在调用外壳之前自行判断的情形（外壳会弹窗并无限等待，无人值守时会卡死，也违背“如实汇报”）：

1. 同名冲突与原文件夹不存在：先检查，直接失败。
2. 对原文件夹没有“新建文件／子文件夹”权限：用 `FILE_ADD_FILE`／`FILE_ADD_SUBDIRECTORY` 打开目录探测（不创建任何东西）；失败按“没有权限”处理。
3. 标识已过期（项目已被别处还原或清除）：检查其回收站内真实文件是否还在，不在按“项目已不存在”处理。

命令返回后一律以结果为准：还原成功当且仅当原位置确实出现了该项；回收成功当且仅当原路径已消失。

### 与目录监视（Issue #7）的关系

本应用发起的操作完成后，用 `refresh_where` 重新读取所有显示受影响目录（及回收站）的标签，选择保留；结果带序号，过期结果会被丢弃，所以即使目录监视也触发了刷新也不会产生重复条目。目录监视合入后：监视负责“外部程序造成的变化”，本机制负责“自己操作后的立即一致”，两者互不依赖。

## 验证与安全

- 单元测试：`src/fileops.rs`（用 `StashBackend`：删入／还原闭环、不支持回收站不永久删除、部分成功汇报、措辞、失败截断、冲突／缺目录／权限、永久删除、符号链接与联接只删链接）。
- 真实回收站测试：`src/recycle/tests.rs`，**只在 `%TEMP%\sfm-unit\recycle-<标签>-<进程号>-<时间>` 夹具上操作**，断言与清理都只认“原位置在该夹具目录内”的回收站项目；清理用不带确认框的 `IFileOperation` 永久删除，结束后核对本测试夹具项目已清空（用户已有的回收站内容一概不碰）。覆盖删入、浏览字段、恢复文件与文件夹、同名冲突、原目录消失、权限不足（`icacls` 拒绝写入）、过期标识、部分成功批量。
- 无人值守防卡死：`scripts/run-recycle-tests.ps1` 带超时看门狗，超时会强杀并报告弹出的系统窗口标题；运行前后统计回收站总数与夹具残留。早先异常中断留下的夹具项目用 `-Filter sweep_stale_fixtures -Ignored` 清扫（只处理 `sfm-unit\recycle-` 下且不属于当前进程的项目）。
- harness：`Env.backend` 注入 `StashBackend`，界面流程（确认、取消、汇报、回收站视图、还原、冲突、失败注入）在无头环境里完整验证，**从不接触系统回收站**。详见 [debug-harness.md](debug-harness.md)。

## 已知限制

- 单次操作逐项同步在工作线程里执行，没有进度条与取消；很多大文件时界面只显示“正在…”（同一时间只允许一个删除或还原操作）。进度与取消留待复制／移动工单一并处理。
- 回收站外壳属性里的“删除时间”按 UTC 换算（实测与删除时刻一致），显示时按本地时区格式化。
- 回收站里的文件夹显示为一项，不能进入浏览其内容（与“还原整体”的语义一致，浏览回收站内容不在本单范围）。
- 云占位文件、被占用文件的删除结果以系统返回为准；失败时按上面的汇报原样呈现。
