# 原生右键菜单与 NanaZip 集成（Issue #9）

产品窗口里的系统右键菜单：直接承载 Windows 外壳的 `IContextMenu` 菜单，NanaZip、OneDrive 等第三方扩展随外壳一起出现。做法来自 Issue #3 的原型，结论见 [research/0003](research/0003-shell-menu-and-cloud-compat.md)。本文记录产品里的实现、实测数据、风险与后续建议。

## 一分钟入口

| 目的 | 命令 |
| --- | --- |

| 真实窗口 + 真实系统菜单 + NanaZip 命令 + GDI 量化（需交互式桌面） | `powershell -File scripts/verify-menu.ps1` |

代码位置：`src/shell_menu/mod.rs`（菜单本体）、`src/shell_menu/drive.rs`（仅 `harness` 特性：自动驱动菜单）、`src/app/mod.rs` 的 `Controller::context_menu`（选择语义与菜单之后的处理）、`ui/*.slint` 的 `context`／`item-context`／`background-context` 回调、`src/bin/harness/menu.rs`（无头场景）、`src/bin/menu-selftest/`（真实窗口自测）。

## 实现

1. **事件到请求**：文件项右键、空白处右键、空文件夹的空白处、Menu 键与 Shift+F10 都进入同一个 `context_menu`。选择语义与资源管理器一致：未选中的项先单选；已选项保持选择（多选作用于全部已选项，按显示顺序）；空白处右键清空选择并作用于文件夹本身；键盘呼出时有选择则作用于选择，否则作用于文件夹，且不改变选择。双栏时在非活动面板上右键同时切换活动面板。无权限文件夹的错误面板上鼠标右键不呼出菜单（菜单键仍作用于该文件夹，由外壳自行处理拒绝访问）。
2. **owner 与焦点**：菜单的 owner 直接是本应用主窗口（前台窗口），不另建隐藏窗口，所以菜单关闭后键盘焦点原样不动。主窗口句柄在事件循环启动后才存在，按需解析；排除 winit 的辅助窗口。
3. **消息转发**：菜单期间临时给主窗口装窗口子类，把 `WM_INITMENUPOPUP`、`WM_DRAWITEM`、`WM_MEASUREITEM`、`WM_MENUCHAR`、`WM_MENUSELECT` 转给 `IContextMenu3`／`IContextMenu2`。不转发的话 NanaZip、“发送到”“新建”这类延迟填充的子菜单是空的。菜单结束立即拆除子类。
4. **命令执行**：`TrackPopupMenuEx(TPM_RETURNCMD)` 返回 0 为取消，只销毁菜单并释放接口；非 0 才 `InvokeCommand`（`CMIC_MASK_UNICODE | CMIC_MASK_PTINVOKE`，带鼠标位置）。不用 `CMIC_MASK_NOASYNC`：它会让属性页等命令阻塞界面线程，而本线程持续泵消息，异步命令可以正常完成。结果统一为 `Outcome`（取消、已执行、执行失败、接管、自带命令），失败会在状态栏给出原因。
5. **打开文件夹接管**：单选文件夹时，“打开”由本应用接管，在当前标签内进入该文件夹，而不是让外壳启动资源管理器。其他“打开”交给外壳（默认应用）。
6. **菜单之后**：命令执行后等待 700 毫秒刷新该面板（仅当仍在原位置，不抢活动面板、不改标签）；任何路径都销毁菜单、释放接口、拆除子类、清空会话状态；菜单期间不持有任何 `RefCell` 借用，并用 `menu_busy` 拒绝重入。
7. **键盘锚点**：Menu 键与 Shift+F10 的菜单锚定在键盘光标所在项的中心（`cursor-index`，实测与选中项中心相差 1 像素），不是鼠标位置。

## NanaZip

NanaZip 作为外壳扩展出现在系统菜单里，本应用只负责承载，不自建压缩逻辑，也不做压缩包浏览器。

- **识别方式**：按顶层菜单项**文本**包含“nanazip”判断（见下文“动词乱码”）。
- **约定的操作**（在受控的 `%TEMP%` 夹具上全部成功，且验证了产物）：
  - 压缩：多选三个文件“添加到 sample.zip”，生成合法 zip，含 3 个条目；单选“添加到 a.7z”，生成 7z（有魔数，内含 a.txt）。
  - 解压：压缩包上“提取到 a\”，解压出 a\a.txt，内容一致。
  - 打开压缩包：出现标题含压缩包路径的 NanaZip 窗口，属于其他进程（进程外承载）。
- **未安装时**：菜单里没有 NanaZip 子菜单，本应用在菜单末尾追加一条灰色提示“未检测到 NanaZip（压缩与解压不可用）”。压缩包文件的“打开”仍交给默认应用。
- **前台窗口被抢走**：NanaZip 与属性对话框执行后会把前台窗口抢到自己的进程，这是外壳命令的正常行为，不是本应用丢焦点。菜单被取消时焦点必定回到文件区（已自动验证）。

## 事件循环在模态菜单期间的行为（已实测）

`TrackPopupMenuEx` 是模态消息循环，期间 Slint 事件循环不运行。实测（菜单保持 1.5 秒）：

| 指标 | 结果 |
| --- | --- |
| 菜单期间 Slint 定时器触发次数 | 0 |
| 菜单期间渲染帧数 | 0 |
| 菜单期间 `invoke_from_event_loop` 投递的闭包执行次数 | 0（投递后延迟约 1.79 秒，即菜单关闭后立即执行） |
| 定时器最大间隔 | 约 1.8 秒（含菜单本身的 1.5 秒） |
| 菜单关闭后 | 定时器、跨线程投递恢复，没有永久卡住，没有重入 |
| 菜单期间再次请求菜单 | 返回 `Busy`，不重入 |
| 属性对话框打开期间 | 命令是异步的，Slint 定时器照常运行（600 毫秒内 14 次） |

结论：模态循环只在菜单打开期间暂停界面（和资源管理器一致），关闭后立刻恢复，不会挂起。代价是菜单期间不能刷新界面：目录监视、缩略图回填等后台工作要通过 `invoke_from_event_loop` 投递，会在菜单关闭后才执行，不会丢失。

## GDI 资源增长（已量化）

用 `GetGuiResources` 在真实窗口上重复弹出并取消菜单，各 30 次：

| 场景 | 每次菜单的 GDI 对象增长 | USER 对象增长 |
| --- | --- | --- |
| 顶层菜单（打开后取消） | 4.0 | 0 |
| 展开 NanaZip 子菜单后取消 | 4.0 | 0 |
| 首次菜单（一次性） | 约 +52 | 约 +12 |

按告警线 8000（进程上限 10000 的 80%）计算，约 1977 次菜单后才触及告警。

**是否需要缓解：不需要主动缓解，已有兜底。**

- 增长固定、很小，每次菜单后检查，达到 8000 时在状态栏提示建议重启。
- 泄漏很可能来自某个第三方扩展自己的位图。我们自己没有创建这些位图，擅自按句柄删除可能误删仍被引用的对象，风险大于收益。
- 若以后观测到更快的增长（例如新增扩展），再考虑：把菜单放到子进程里弹出（见下一节），泄漏随子进程结束而回收。

## 风险

### 第三方进程内扩展的崩溃与挂起

外壳扩展（NanaZip 的 `IContextMenu` 实现、OneDrive、各类杀毒与云盘扩展）是被加载到**本进程**里的 DLL。它们在 `QueryContextMenu`、`InvokeCommand`、`WM_INITMENUPOPUP` 里崩溃会带走整个文件管理器；挂起会冻结界面线程。资源管理器自己也有同样的风险，但它有更完整的隔离与超时处理。

当前的缓解：

- 菜单构建耗时超过 500 毫秒会记日志（`SLOW_BUILD`），便于定位慢扩展。
- 菜单构建与命令执行都在 UI 线程，失败以 `HRESULT` 报告到状态栏而不是崩溃。
- NanaZip 的窗口由其自己的进程承载（“打开压缩包”实测为其他进程）。

**后续建议（未实现）**：把菜单构建与弹出放到一个独立的子进程（外壳菜单宿主）里：主进程只传路径与锚点，子进程返回“取消／已执行／失败”。崩溃或挂起只影响子进程，可超时杀掉；GDI 泄漏也随之回收。代价是子进程的窗口 owner 与焦点要用主窗口句柄重新设置，并要处理“文件夹接管打开”等需要回主进程的结果。建议单独立 Issue，先观测真实使用中的崩溃与耗时日志再决定。

### OneDrive 动词乱码

OneDrive 等扩展的 `GetCommandString` 动词返回乱码，不能按动词识别第三方命令。本实现按**菜单项文本**识别（NanaZip 的子菜单与命令均按文本路径匹配），自动测试里也同样按文本。文本会随界面语言变化：目前只在简体中文系统上验证，其他语言的 NanaZip 文本路径未验证。

### 其他边界

- **Windows 11**：未验证。当前机器为 Windows 10 19045，传统菜单就是完整菜单。Windows 11 的新式菜单与“显示更多选项”的关系、第三方扩展在 11 上是否仍完整出现，都没有实测，已列入验收清单。
- **云占位文件**：菜单本身不会触发下载，但“打开”“复制”等命令会，这属于明确的用户操作。
- **删除**：外壳菜单里的“删除”由外壳执行（进回收站），应用内的删除确认、永久删除、回收站浏览与还原由 Issue #8 负责（Delete／Shift+Delete 与工具栏）。外壳菜单的删除不经应用内确认框，但命令执行后目录会被刷新。
- **回收站视图**：回收站是虚拟位置（`shell:RecycleBinFolder`），没有磁盘路径可交给外壳菜单，所以在回收站里右键与菜单键只处理选择，不呼出菜单；还原、清空走视图自己的按钮（无头场景 K 覆盖）。
- **只在临时夹具上验证**：自动测试从不触碰用户文件。

## 验证覆盖

- **无头**（`harness run` 的 `context` 场景，11 步）：未选中项右键先单选、已选项右键保持多选、多选时在未选项上右键改为单选、文件夹接管“打开”、Menu 键与 Shift+F10、空白处右键清空选择、无选择时键盘作用于文件夹、空文件夹也能呼出、无权限错误面板、双栏非活动面板、回收站不呼出菜单。
- **真实窗口**（`verify-menu.ps1`，263 项检查）：真实 Win32 右键／Menu 键经 winit 到 Slint；菜单真实弹出；取消后无残留（无活动会话、无窗口子类、无残留菜单窗口）、焦点回文件区、前台窗口仍是主窗口；消息转发统计；NanaZip 压缩、解压、打开及产物；新建文件夹；属性对话框；文件夹打开接管；未安装 NanaZip 的提示；重入拒绝；事件循环与 GDI 量化。
- **不能自动证明的**：真人鼠标与键盘的手感、菜单位置的视觉观感、Windows 11、多显示器与高 DPI 混用，这些在 `docs/checklist/checklist.md` 里。
